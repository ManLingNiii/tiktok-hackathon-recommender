You are an autonomous feature-research agent for the History track of a
recommender-system competition.

Your task is to propose candidate HISTORY FEATURES for a within-user ranking
model. Decide WHAT should be computed first. Do not invent feature IDs or
feature names: the pipeline will derive standardized identifiers from the
complete computation specification after validation.

## Baseline fields

The existing FM baseline already uses these fields:

- user_id
- video_id
- author_id
- tab
- dur_bucket

History proposals should add information derived from prior interactions. Do
not simply repeat the baseline fields.

## Available source columns

You may use only these source columns:

- user_id
- video_id
- author_id
- tab
- date
- hourmin
- time_ms
- duration_ms
- long_view
The following engagement columns are explicitly excluded from the History
track because they belong to or overlap with the Multi-task track:

- is_click
- is_like
- is_follow
- is_comment
- is_forward
- is_hate
- play_time_ms
- profile_stay_time
- comment_stay_time
- is_profile_enter
- is_rand

They must not be proposed as current-row inputs or aggregated over history.

## Mandatory constraints and safeguards

1. Use only the official training split to construct historical state.
2. History must be chronological: only interactions before the current row may
   contribute to its feature value.
3. Do not use validation or test rows, labels, or future interactions while
   constructing a feature.
4. Do not use hidden test labels, external data, pretrained information, or
   any forbidden source.
5. Set `uses_current_row` to false. The current row must not contribute its
   own label or outcome to its feature.
6. The feature must affect within-user candidate ranking. It must reference
   or interact with a candidate-side field such as video_id, author_id, tab,
   duration_ms, or dur_bucket. Reject pure user-only statistics because they
   are constant across a user's candidates and cannot change ranking order.
7. Define the history window explicitly, including whether it is all prior
   training history or a fixed recent window.
8. Define how empty history is handled and how smoothing, clipping, or
   normalization is performed.
9. The formula must be deterministic and implementable from the listed
   columns.
10. Prefer features that are distinct from one another and explain what
    additional behavioral signal they capture.
11. If training-only coverage estimates are supplied with this prompt, use
    them to prefer features likely to meet the 5% minimum. Treat estimates as
    guidance, not proof.
11. Use only these supported aggregation values: `smoothed_positive_rate`,
    `interaction_count`, `duration_bucket_affinity`, or
    `recency_weighted_positive_rate`.
12. Use only these supported window types: `all_prior` or `recent`.
    Unsupported computation types must not be proposed.

## History-track column boundary

A valid History feature may use only these categories:

- identity/candidate: user_id, video_id, author_id
- context: tab
- time: date, hourmin, time_ms
- duration: duration_ms
- historical outcome: long_view, only from prior training interactions

The excluded engagement columns above are present in the raw dataset but are
not valid History-track columns. This separation ensures that History models
measure temporal user-candidate interaction patterns, while Multi-task models
own auxiliary engagement objectives.

## Required output

Return JSON only. Do not include Markdown, commentary, feature IDs, or bare
feature names. Return between 3 and 8 candidate specifications in this exact
shape:

{
  "features": [
    {
      "source_columns": ["author_id", "long_view"],
      "history_scope": "prior interactions from the official training split for this user and candidate author",
      "time_order": "strictly earlier interaction time than the current row",
      "window": {"type": "all_prior", "value": null},
      "aggregation": "smoothed_positive_rate",
      "formula": "(prior long_view positives for the user-candidate-author pair + 20 * global training long_view rate) / (prior pair interactions + 20)",
      "uses_current_row": false,
      "rationale": "Captures whether the user historically engaged positively with this candidate author."
    }
  ]
}

Before returning each feature, check it against every constraint above. If a
proposal is pure user-side history, uses future/current-row information, or
cannot vary with the candidate, do not return it. Ensure that two features
with the same source columns, window, aggregation, and formula are not
duplicated under different wording.

Coverage policy:

- The minimum validation coverage is fixed at 5% before the official
  validation run.
- Do not choose or revise this threshold using official validation results.
- Prefer broader candidate keys when training-only estimates suggest that an
  exact-match feature will be too sparse.
- The execution pipeline calculates actual validation coverage and rejects any
  proposal below 5% before model training.
